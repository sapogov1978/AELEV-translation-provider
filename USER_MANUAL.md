# Руководство translator-service

## Отдельный образ издателя

`AELEV_INFRASTRUCTURE_TRANSLATOR_UI_IMAGE` выбирает собственную цель `status-runtime`: модельные веса и нативный движок в неё не входят. Закреплённый `aelev-platform-ui-client==1.1.1` проверяет живость командой `python -S /opt/aelev/publisher-health.py AELEV_INFRASTRUCTURE_TRANSLATOR_`, читая только подтверждённый heartbeat собственного журнала без загрузки приложения и сетевых запросов. Обновляйте только `translator-service-status-publisher`, сохраняя его том; перед этим согласуйте env и отдельные файловые identities с текущим Compose, не копируйте секреты другого владельца и не ослабляйте TLS. Такая проверка не подтверждает готовность модели и не устанавливает автовосстановление по `unhealthy`.

Локальный Swagger без установки клиентского сертификата: [полная настройка и команды](USER_MANUAL.md#группы-и-операции-swagger). Откройте `http://127.0.0.1:18496/docs`, нажмите `Authorize` и войдите через существующий Keycloak своим оператором с назначенным `operator-read`. Без собственного токена операции возвращают 401; право оболочки не заменяет право API. HTTP допускается только в явно выбранной локальной установке на loopback, не для удалённого сервера. IdP сохраняет HTTPS, корпоративные ограничения браузера не обходятся.

Общий инфраструктурный компонент выполняет технические задания на перевод и не знает, какой клиент или предметный процесс использует результат. Межсервисные задания и результаты проходят только через принадлежащие translator-service Kafka topics. Операторский Swagger по [ADR-0109](../../../docs/adr/20261011-0109-operator-translation-through-kafka.md) может отправить собственный запрос в ту же очередь и дождаться перевода; частный HTTP backend остаётся только для диагностики.

## Установка и запуск

Исходники, собственная PostgreSQL, миграции, закреплённые схемы, `compose.yml` и `.env.example` находятся в этом каталоге. Команды ниже выполняются из него после подготовки env, файлового пароля и выбранного TLS/OIDC-режима по [README](USER_MANUAL.md#установка-и-запуск). Существующие настройки и секреты не перезаписывайте. Обычный запуск автоматически поднимает Kafka из соседней канонической поставки, ждёт её готовности и применяет topics; вручную запускать provisioner не требуется. Если тома уже заняты корневой оркестрацией, используйте её проект, а не создавайте второго писателя. Секреты не публикуются.

```sh
docker compose --env-file .env config --quiet
docker compose --env-file .env up --build -d --wait --wait-timeout 600
docker compose --env-file .env ps
```

`translator-migrator` выполняется до рабочих ролей и не повторяется бесконечно. `translator-topic-provisioner` ждёт healthy Kafka, при ошибке соединения повторяется и не пропускает consumer, outbox или API дальше. `translator-model` и `translator-api` должны стать healthy; оба consumer, worker и outbox должны работать. Новые задания сохраняются даже при временной недоступности модели. Перезапуск вычислительной ячейки не требует перезапуска клиентов.

Если Kafka находится на другом сервере, используйте `compose.remote.yml`: он не запускает Kafka на узле переводчика и проверяет реальный endpoint. Защищённый broker должен уже существовать: текущий локальный Kafka Compose не добавляет TLS автоматически. Для удалённой PostgreSQL задайте маршрутизируемый `DATABASE_HOST`, `DATABASE_NETWORK_INTERNAL=false`, `DATABASE_SSLMODE=verify-full` и доставьте CA/client certificate/key в отдельный `DATABASE_SECRET_ROOT`; production с `disable`, `require` или `verify-ca` закрыто отклоняется. Локальный режим сохраняет собственную БД, internal network и `sslmode=disable`. Несколько model/worker-ячеек могут находиться на разных hosts, но каждая пара использует только свой локальный Unix socket; consumer и outbox не размножаются произвольно.

## Что происходит с заданием

Обычный независимый запрос `TranslationRequestedV2` содержит текст, исходный и целевой языки и техническую идентичность запроса, без модели, её версии или операции исполнения. Срочный запрос публикуется в `translation.requests.priority.v2`, обычный — в `translation.requests.v2`; payload у них одинаков. Consumer сохраняет запрос, worker выбирает текущее исполнение для своей ограждённой попытки, а outbox публикует `TranslationCompletedV2` без раскрытия исполнителя. Новый перевод может отличаться после обновления или переобучения. Для повторной доставки уже завершённого технического запроса возвращается сохранённый ответ. V1 остаётся только для миграционного завершения старых клиентов.

`PENDING` означает ожидание, `RUNNING` — активную попытку, `SUCCEEDED` — готовый результат, `FAILED` — доказуемую ошибку входа или непригодный выход модели. Временный технический сбой автоматически повторяется и не создаёт отменённой карточки. Готовый перевод ещё не доказывает правильность смысла; итоговую проверку локализации выполняет её владелец.

## Статус, пауза и продолжение

### Порядок очереди и повторы

Планировщик сохраняет исходный возраст технического задания по [SPEC](SPEC.md#вход-и-вычисления). Пауза перед повтором временно делает его недоступным, но не меняет место среди допущенных заданий своего класса. Очередь состоит из отдельных строк, не целых локализаций; готовность полного языка определяет его владелец после получения всех результатов. Более поздний перевод всё ещё может завершиться раньше, если старый находится на паузе или выполняется другой ячейкой.

Для разбора смотрите у самого переводчика `translation_job.created_at`, `available_at`, `state`, `attempt_count` и `error_code`; не сравнивайте только время последнего изменения локализации у клиента. Журнал `translation_model_retry` содержит тот же ограниченный код и корреляцию без текста. `TRANSLATOR_DEADLINE_EXCEEDED` означает timeout, `TRANSLATOR_NATIVE_NOT_READY` — незавершённую загрузку, `TRANSLATOR_NATIVE_UNAVAILABLE` — отказ нативного вычислителя, `TRANSLATOR_MODEL_UNREACHABLE` — недоступный частный socket. `TRANSLATOR_MODEL_HTTP_ERROR` не раскрывает произвольное тело ответа; `TRANSLATOR_UNAVAILABLE` обозначает неизвестную причину, в том числе исторические записи до уточнения диагностики. Новый код ожидайте только после новой попытки; повтор всей локализации не нужен для исправления порядка уже принятых строк.

Исправление сортировки и кодов не требует новой ревизии БД, RESET, переписывания `created_at`/`available_at`, сброса Kafka offsets или повторного вычисления готовых ответов. После штатного завершения активной попытки и обновления совместимых model/worker проверьте новый lease среди самых старых допущенных заданий, сохранение возраста и результат через outbox. Сам факт взятия в работу не доказывает успешность перевода.

### Группы и операции Swagger

В `/docs` группы расположены в порядке `default`, `translator`, `metrics`. Операторский режим требует собственной авторизации по [README](ENDPOINTS.md); группировка не меняет права доступа или ответы.

| Группа | Endpoint | Что показывает |
|---|---|---|
| `default` | `GET /healthz` | API отвечает. Это не проверка БД, Kafka или модели. |
| `default` | `GET /readyz` | Собственная БД, broker Kafka и три topics доступны; при отказе — 503. Готовность модели и продвижение заданий этим не подтверждаются. |
| `default` | `GET /v1/components` | Наблюдения присутствия `priority-consumer`, `normal-consumer`, `worker`, `outbox`, `model`: `state` и время `observed_at`. Устаревшее/отсутствующее наблюдение означает `UNKNOWN` и `observed_at=null`, а не доказанную остановку. |
| `default` | `GET /v1/status` | `control.desired_state` — разрешена ли выдача новых заданий; `revision` — ревизия управления; `priority_streak` — текущая серия срочных выдач. `jobs` содержит числа заданий по состоянию и очереди, например `PENDING:normal`. Отсутствующая комбинация означает отсутствие таких заданий. |
| `translator` | `POST /v1/translate` | Операторский перевод через выбранную очередь Kafka. Требует отдельного `operator-translate`; частный listener не предоставляет этот endpoint. |
| `metrics` | `GET /metrics` | Числа заданий в формате Prometheus: `aelev_translator_jobs` с метками `state` и `queue`. |

`/v1/status` и `/v1/components` полезны вместе: очередь может накапливаться при живых исполнителях, а API может отвечать при отсутствующем worker. Heartbeat означает присутствие, не отсутствие зависания или успешное вычисление; модель проверяется внутри собственной вычислительной ячейки. Эти ответы не содержат текстов заданий, готовых переводов или сведений о клиентах и не заменяют итоговую проверку качества перевода.

### Управление выдачей заданий

Команды выполняются только человеком с разрешённым эксплуатационным доступом к инфраструктуре. CLI не является публичным HTTP-интерфейсом и не даёт доступ к чужим хранилищам. Прочитайте состояние и текущую ревизию:

```sh
curl --fail http://127.0.0.1:8096/v1/status
```

Чтобы прекратить выдачу новых заданий, сохраните PAUSE с уникальным идентификатором, своей идентичностью, причиной и ожидаемой ревизией. Активная единица может завершиться. Вместо PAUSE используйте RESUME для продолжения; ожидаемую ревизию берите из нового статуса, а не копируйте прежнее число.

```sh
docker compose --env-file .env exec translator-priority-consumer \
  python -m translator_service.runtime control \
  --action PAUSE --command-id maintenance-1 --actor operator \
  --expected-revision 1 --rationale planned-maintenance
```

RESET возвращает только незавершённую работу в очередь. Сначала выполните PAUSE и дождитесь отсутствия активных аренд, затем отправьте RESET с текущей ревизией, новым идентификатором и причиной; после этого отправьте RESUME. Готовые результаты и история не стираются. Конфликт ревизии требует перечитать статус. Повтор того же идентификатора допустим только с точно тем же телом команды.

## Операторский перевод

Владелец сначала явно включает `API_TRANSLATION_ENABLED=true` и выполняет настройку из [README](USER_MANUAL.md#операторский-перевод). При `false` POST не показывается и недоступен; пять диагностических GET сохраняются. В текущем локальном стенде операторский перевод включён.

Настройте собственные OIDC и пределы по [README](USER_MANUAL.md#операторский-перевод), выполните `translator-api-provision` и войдите через `Authorize`. Настроенному `API_OPERATOR_USER` задача явно назначает два отдельных права; прочие пользователи не получают право перевода автоматически. `operator-read` позволяет читать диагностику, но не отправлять текст; `operator-translate` разрешает POST, но не подменяет право чтения. В HTTPS-режиме клиентского сертификата для POST недостаточно: нужен также собственный токен.

Откройте `translator` → `POST /v1/translate` → `Try it out`, замените тело запроса и нажмите `Execute`:

```json
{
  "source_language": "en",
  "target_language": "de",
  "queue": "normal",
  "text": "Hello, world!"
}
```

`source_language` — код исходного языка, `target_language` — код целевого языка. Коды используют строчные буквы и собственный протокол модели, например `en`, `de`, `ru`. `queue` выбирает только `normal` или `priority`; срочность не означает прерывание уже выполняющегося задания. `text` — точный исходный текст до 12 000 символов, не только пробелы. Для приоритетного задания замените `normal` на `priority`; имя topic, чужой идентификатор и модель передавать нельзя.

Ответ 200 содержит перевод в `translated_text`, UUID `request_id`, языки, очередь, точный `translator_ref` и предупреждения `warnings`. Ответ появляется после полного штатного пути и Kafka ACK результата, не после прямого обращения к модели. Действующая модель — Index-Translate 9B; её точный выпуск выбирается автоматически из собственного lock. Готовый текст не доказывает смысловую точность: проверяйте результат так же, как любой иной перевод. Поддерживаемые языковые коды, ограничения и смена модели описаны в [README](SPEC.md).

Если получили 429, API отказал до постановки из-за текущей нагрузки. 422 сообщает неверный ввод или доказуемую ошибку перевода. 503 может означать неподтверждённую доставку, а 504 — превышение времени ожидания; в этих случаях задание могло остаться в очереди и продолжить работу. Отключение браузера его не отменяет. Сохраните `detail.request_id` для диагностики; не воспринимайте ошибку ожидания как доказанную отмену. Каждый новый POST — новое намерение и новое задание, а не идемпотентный повтор; автоматической повторной отправки нет. Точная таблица ошибок и пределы находятся в [контракте](../../../docs/api/translation.md#операторский-перевод).

## Диагностика и восстановление

### Согласованное обновление схемы

Отдельный образ издателя не означает независимость от схемы собственной БД. До обновления сверяйте фактическую `alembic_version`, `schema.HEAD` выбранного выпуска и единственную вершину его Alembic: SQL-роли и издатель должны ожидать один head. Запуск нового издателя поверх прежней БД не является полной выкладкой. Не обходите точный schema gate и не используйте `stamp` вместо DDL.

Сначала соберите и проверьте выбранный выпуск, сохраните прежние image digest, модели, пароль, имена consumer groups и управляющее состояние. Для локального обслуживания при неизменной модели доступна цель `translator-runtime-update`: аргумент `AELEV_INFRASTRUCTURE_TRANSLATOR_RUNTIME_SEED_IMAGE` обязан указывать предыдущий доверенный образ самого переводчика как `image:tag@sha256:<digest>`. Она сохраняет его ОС, веса и движок, но сначала удаляет прежние каталоги приложения внутри нового образа, затем заменяет полный текущий код, окружение Poetry, контрактный артефакт, Swagger и миграции; модель проверяется по lock/SHA-256. Незакреплённый тег отвергается сборкой, а происхождение и доверие к собственному seed проверяет оператор; образ другого сервиса использовать запрещено. Обычный чистый запуск по-прежнему собирает последнюю цель `translator-runtime` без зависимости от старого выпуска; эта ветвь обслуживания не является обновлением ОС или модели.

Перед сменой схемы прекратите приём/API/outbox и штатно дренируйте worker; активная попытка должна завершиться либо истечь с ограждением. При обслуживании явно задавайте `stop --timeout 120` для API/consumers/outbox и `stop --timeout 250` для worker, проверяйте коды завершения и отсутствие действующих попыток; принудительное завершение не называйте штатным. Если издатель зарегистрирован в host recovery, выполните его `suspend` до обслуживания. Сохранённое `desired_state` не меняйте через RESET. Создайте новый приватный `pg_dump`, восстановите его в отдельной изолированной БД без Kafka и проверьте прежним совместимым `verify-restored-state`. Дополнительно `deployment/check_state.py` сохраняет SHA-256 точных строк всех собственных таблиц, не выводя тексты и credentials. Его диагностическое чтение обеих ревизий не отменяет schema gate рабочего приложения.

Миграцию `0004 → 0005` сначала примените на восстановленной копии. `check_state.py --before <frozen-0004.json> --output <new-0005.json>` разрешает только новый пустой `translation_segment` и смену `alembic_version`, требуя побайтно прежнего содержимого остальных таблиц. Новый `verify-restored-state` должен подтвердить запросы, результаты и outbox. Деструктивные фикстуры Pytest запускайте в другой пустой `translator_test`, не в рабочей БД и не в единственной проверенной восстановленной копии.

Только после репетиции примените тот же migrator к замороженной рабочей БД и повторите сверку до запуска писателей. Затем адресно обновите модельную ячейку и все SQL-роли выбранным единым image digest, дождитесь настоящей готовности модели, выполните штатную проверку topics без изменения параметров и запустите прежние consumers/outbox/API/worker. Пароль, SQL-права, TLS-режим, Kafka offsets, готовые результаты и управляющее состояние сохраняются. Runtime получает только собственные смонтированные secret-каталоги; `AELEV_INFRASTRUCTURE_TRANSLATOR_SECRET_GID` задаёт дополнительную группу чтения без world-readable файлов или запуска от root.

Завершение требует точного head во всех ролях и БД, успешных `/healthz`/`/readyz`/`/runtimez`, свежих собственных heartbeat и реальной публикации нового состояния в Platform UI, а не только зелёной локальной пробы. Сохраните том/identity/последовательность издателя и явно возобновите его регистрацию в ограничителе после проверки; попытки не обнуляйте автоматически. Для отката после 0005 требуется совместимый образ с поддержкой новой схемы либо отдельное согласованное восстановление: `downgrade` не удаляет checkpoints и не возвращает старых писателей поверх новой ревизии.

```sh
docker compose --env-file .env logs --tail 30 \
  translator-priority-consumer translator-normal-consumer \
  translator-worker translator-outbox translator-model
docker compose --env-file .env exec translator-priority-consumer \
  python -m translator_service.runtime health
```

При недоступности БД consumer не подтверждает Kafka offset и перезапускается; после восстановления он продолжает с сохранённой позиции. Длинный текст разбивается на устойчивые сегменты: после timeout или истечения lease новая совместимая попытка использует уже завершённые checkpoints и продолжает с первого незавершённого сегмента. Смена `execution_ref` закрыто удаляет несовместимые промежуточные переводы, поэтому сегменты разных выпусков не смешиваются. При недоступности модели задание повторяется автоматически, при зависании вычисления срабатывает ограниченный timeout. Неподдерживаемый язык или неверный контракт не принимаются за успешную локализацию: проверьте технический код и точную модель, не подменяйте результат вручную. Обычные логи не содержат исходных текстов, SQL или паролей.

Резервную копию своей БД восстанавливайте в отдельный изолированный экземпляр, без доступа к рабочим topics. Сохраните точные схемы и модель. Проверка `python -m translator_service.runtime verify-restored-state` должна вернуть `VERIFIED`; она не исправляет и не публикует данные. Незавершённые аренды после восстановления повторяются, готовые результаты сохраняются. Порядок и команды изолированной проверки приведены в [README](README.md).

В local `OTLP_HTTP_ENDPOINT` может быть пустым. Для production доставьте отдельные client и sender mTLS-файлы в `TELEMETRY_SECRET_ROOT`, задайте `OTLP_HTTP_ENDPOINT=https://translator-telemetry-sender:4318`, подготовьте постоянный том командой `docker compose --profile provision run --rm translator-telemetry-data-init` и запустите профиль `telemetry`. Runtime не получает identity центральной доставки, а sender не получает Kafka-admin, database или OIDC-admin secrets. При недоступности центрального delivery записи остаются в собственном persistent journal.

Для адресной штатной остановки из этого каталога используйте `docker compose --env-file .env stop translator-priority-consumer translator-normal-consumer translator-worker translator-outbox translator-model translator-api`. Не удаляйте БД, Kafka-журналы, сегментные checkpoints или volumes: остановка процесса не означает удаление истории. Production требует защищённых endpoints и отдельных identities; локальный PLAINTEXT не переносится в production.
