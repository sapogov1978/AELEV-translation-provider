# translator-service: нормативная спецификация

Издатель использует отдельный собственный образ `AELEV_INFRASTRUCTURE_TRANSLATOR_UI_IMAGE`, цель `status-runtime` без модельных весов и нативного исполнителя. Его Docker-проба запускает автономный файл `health.py` из закреплённого `aelev-platform-ui-client==1.1.1` через `python -S`, читает только собственный подтверждённый heartbeat и UUID. Она не импортирует приложение, не выполняет PostgreSQL/Kafka/TLS-запросы и не меняет прежний предел свежести. Минимальный локальный предел памяти этой роли составляет 256 MiB, чтобы повторяющиеся ограниченные TLS-попытки при недоступном приёмнике не завершали издатель по OOM; это не резерв памяти доменного сервиса. Готовность переводчика по-прежнему определяется собственными компонентами, не успехом контейнерной пробы издателя.

Необязательное время выполнения v2-результата измеряется монотонными часами только вокруг исполнения строки, до записи и публикации результата, по [контракту](../../../docs/api/translation.md#измерение-времени-выполнения). Оно не включает очередь, прежние незавершённые вычислительные попытки или повторную доставку; сохранённый результат и его измерение воспроизводятся побайтно. Внутренняя модель остаётся неизвестной потребителю, v1 не расширяется.

По [ADR-0109](../../../docs/adr/20261011-0109-operator-translation-through-kafka.md) операторский listener дополнительно принимает `POST /v1/translate` с отдельным OIDC-правом `operator-translate`. Прежние ограничения read-only ниже относятся к частному listener и диагностическим GET, а не к этому явно согласованному исключению. Вход публикуется только через штатный Kafka topic, не прямой записью задания или вызовом модели; API читает свой точный результат после ACK outbox. Определения входа, пределов, ошибок и неидемпотентного нового POST находятся в [контракте](../../../docs/api/translation.md#операторский-перевод). Перевод не является межсервисным HTTP-интерфейсом, а API не становится владельцем второго источника данных.

Локальное исключение операционного API по [ADR-0108](../../../docs/adr/20261011-0108-loopback-operator-http.md) выбирается явно HTTP origin в собственной конфигурации только при `ENVIRONMENT=local` и опубликованных loopback-портах. Документация/схема публичны, пять диагностических GET требуют собственного OIDC access token и client role `operator-read`; POST по ADR-0109 требует отдельного `operator-translate`. Issuer, audience, authorized party, подпись и сроки проверяются владельцем. HTTPS остаётся mTLS-режимом с дополнительным OIDC для POST, без автоматического HTTP при ошибке TLS. IdP сохраняет проверенное HTTPS, callback и origin точны, PKCE S256 обязателен. Административные OIDC-учётные данные доступны только собственной одноразовой задаче `provision`, не API. Исключение не касается межсервисного Kafka, iframe или удалённого размещения; прочие требования TLS ниже относятся к HTTPS-режиму.

Присутствие собственного издателя, штатная подтверждённая отписка и потеря связи определяются только [каноническим UI-контрактом](../../../docs/api/platform-ui-injection.md#присутствие-и-штатная-отписка) и ADR-0105. Отписка скрывает модуль без удаления журнала или изменения ревизии; отсутствие публикаций без отписки оставляет строку с потерей связи. Повтор и восстановление сохраняют владельца, UUID, последовательность и точные неподтверждённые байты.

Собственное состояние инъектируется по [техническому UI-контракту](../../../docs/api/platform-ui-injection.md) отдельной ролью `ui`: тип INFRASTRUCTURE, собственные БД, Kafka-соединение, consumers, единая вычислительная модель, outbox, API и издатель. Внутренние model и worker одной вычислительной ячейки не публикуются как два пользовательских компонента: одна строка «Вычислительная модель» агрегирует оба наблюдения, получает `ONLINE` только при готовности обоих процессов, `OFFLINE` при подтверждённой недоступности любого из них и `UNKNOWN` при неполном или неопределённом наблюдении. Раздельные model/worker остаются в техническом `/v1/components`. Пользовательское название компонента не раскрывает семейство модели; точный выпуск остаётся в владельческом lock и диагностике. Наличие UI/IdP не является зависимостью нативного запуска. Источник присутствия — только собственные heartbeat, локальная проверка модели в ячейке и явное владельческое `COMPUTE_DESIRED_STATE`: `STOPPED` публикует единый компонент как `OFFLINE`, а при `RUNNING` успешная точная `/runtimez`-проверка локального Unix socket даёт `ONLINE`, отсутствующий или отвергающий соединение socket — `OFFLINE`, timeout, невалидная identity или ответ — `UNKNOWN`. Техническая таблица `translation_runtime_presence` принадлежит переводчику, перестраивается следующими heartbeat и хранит строки сутки. TTL задаёт неизвестность, не удаление заданий или канонических результатов; heartbeat доказывает присутствие, не продвижение основной очереди. Единственная новая DDL применяется мигратором, не рабочими ролями. БД других сервисов и Docker API не читаются. Смысл read-only API и сохранность определены в [контракте](../../../docs/api/translation.md).

Общий инфраструктурный компонент владеет контрактом перевода, двумя входными и одним выходным topic каждой версии v1/v2, вычислением, закреплённой автономной Index-Translate 9B, собственной PostgreSQL-очередью и результатами. Назначение текста и решения клиентов он не знает и не изменяет. Публичная граница задана [Kafka-контрактом](../../../docs/api/translation.md), размещение и поставка — [ADR-0096](../../../docs/adr/20261009-0096-consumer-agnostic-scalable-translator.md), выбор вычислителя — [ADR-0112](../../../docs/adr/20261011-0112-index-translate-9b.md).

## Вход и вычисления

По [ADR-0124](../../../docs/adr/20261013-0124-provider-owned-translation-execution.md) действующий публичный запрос v2 содержит только текст, языки и техническую корреляцию. Собственный `execution_ref` записывается в БД при аренде каждой попытки и отсутствует в публичном запросе и результате. Незавершённое задание после обновления может выполняться текущим исполнителем; новый перевод может отличаться. Исторический ответ сохраняется, а повторная доставка того же завершённого технического сообщения остаётся идемпотентной. V1 принимается дополнительно для миграционного завершения старых клиентов и воспроизведения прежних результатов; новые клиенты используют v2.

Миграционный вход — `TranslationRequested` v1 через `translation.requests.priority.v1` или `translation.requests.v1`. Схема проверяет техническую identity издателя, но не закрепляет список клиентов. Отдельный consumer каждого topic проверяет артефакт схем, время, SHA-256 текста и идентификатор, транзакционно сохраняет точные байты до Kafka commit. Приоритет определяется только topic: 0 для приоритетного и 100 для обычного. Конфликт идентификатора или неверный контракт сохраняется в собственном карантине. При отказе БД consumer прекращает работу без commit и читает от последнего подтверждённого offset после перезапуска.

Работник получает одно задание с отдельным token и lease 360 секунд, используя `FOR UPDATE SKIP LOCKED`. Под блокировкой управляющей записи счётчик допускает не более настроенного количества последовательных приоритетных leases, после чего при наличии выдаётся обычное задание. Внутри класса допущенные задания выдаются по неизменяемому `created_at`, затем `request_id`; `available_at` только запрещает преждевременный повтор и не является ключом сортировки. Технический повтор сохраняет исходную дату и байты задания, поэтому после паузы оно не попадает в хвост. Во время паузы разрешена другая готовая работа; завершение переводов не обязано следовать порядку поступления, особенно между ячейками. Просроченное задание может быть выдано вновь; завершение прежнего token запрещено. Текст детерминированно делится по абзацам и пределу 800 символов; таблица `translation_segment` хранит порядковый номер, точный источник и digest, `execution_ref`, готовый перевод и warnings каждого сегмента. Завершение сегмента продлевает только действующий ограждённый lease. Новая попытка с тем же execution продолжает с сохранённых checkpoints, а смена execution удаляет несовместимые сегменты до вычисления. Внутренний вычислительный запрос ограничен 240 секундами, отдельный сегмент — 180 секундами. Зависший дочерний процесс прекращается и запускается заново; вычисления выполняются без внешней сети, веса проверяются по размеру и SHA-256 закреплённого `translator.lock.json`.

Независимый клиент отправляет `TranslationRequestedV2` с исходным языком, целевым языком и текстом, без поля операции или исполнителя. Прежние `PROFILE_UNIT` и `OPERATOR_REVIEW` сохраняются только как совместимые значения v1. Независимые задания не смешивают входы или модельный контекст. По [ADR-0170](../../../docs/adr/20261028-0170-uniform-owner-compute-station-entry.md) вычислительная ячейка состоит из локальной пары model + worker и собственного Unix socket, определяется только самодостаточным `compose.compute.yml` и отсутствует в основном Compose. Единый station entry принимает immutable image reference, запрещает remote Docker context и разделяет `doctor`, `prepare`, `start`, `status`, `stop`; добавление одинаковых ячеек увеличивает пропускную способность без общего socket между узлами. Полный оригинал остаётся у клиента; перевод не входит в обучение как независимая метка.

Проверка готовности вычислителя успешна только после подтверждённой загрузки модели дочерним runtime. Канонический `/healthz` частного процесса сообщает только живость по [общему контракту](../../../docs/api/health-readiness.md), а owner-private `/runtimez` подтверждает готовность и точный `translator_ref`. Docker-проба модели читает только атомарный локальный heartbeat из `/tmp`: сигнал создаётся циклом обслуживания после той же подтверждённой загрузки и содержит инкарнации Python-процесса и его нативного дочернего процесса. Автономный `python -S` с импортами только `os` и `time` проверяет формат, владельца файла, обе живые инкарнации и свежесть до 30 секунд; FIFO, ссылки, зомби-процесс, смерть, подмена PID и устаревший сигнал отвергаются. Повтор HTTP-запроса или импорт `httpx` при Docker-опросе не выполняется. Во время перезапуска или загрузки runtime существующий процесс остаётся живым, но не считается готовым, а устойчивый вход и очередь не теряются.

Docker-проба API использует тот же автономный файл, но подтверждает только работающий общий цикл и оба запущенных listener. Она не проверяет БД, Kafka, модель или продвижение очереди: готовность зависимостей остаётся отдельным `/readyz`. Остановка одного listener завершает оба и отзывает сигнал; зависший цикл не обновляет heartbeat. Сигналы не являются каноническими данными, живут в собственном tmpfs и удаляются при штатном завершении; интервал Docker 10 секунд, timeout 5 секунд и прежние числа отказов модели/API 30/12 сохранены.

## Устойчивый результат

Docker-пробы обоих consumers, worker и outbox читают автономный локальный сигнал через `python -S`; они не загружают SQLAlchemy, HTTP/Kafka-клиенты или приложение и не обращаются к зависимостям. Сигнал атомарно обновляет только основной цикл, а не независимый поток присутствия. Пауза или пустая очередь остаются живым состоянием. Обычное окно свежести — 30 секунд; явно обозначенное ожидание Kafka у consumer допускает 120 секунд, отдельное обращение worker к модели — 300 секунд при прежнем запросе до 240 секунд. Окно не продлевается фоновым потоком; новый сегмент получает его только при фактическом переходе основного цикла к следующему вызову. Неизвестная фаза, устаревшая отметка, смерть или повторное использование PID закрывают пробу. При штатном завершении сигнал отзывается. Проба подтверждает живость, не успешную обработку или доступность зависимости.

Все свежие собственные Python runtime и издатель используют SQLite 3.53.4 с закреплённым архивом и проверенным SHA3 исходного `sqlite3.c`; ABI подключается без замены Python, ОС, SDK и схемы журнала. Адресные maintenance-цели Docker сохраняют слои прежнего собственного образа. Отдельный `BACKGROUND_IMAGE` выбирает только четыре фоновые роли и не переключает работающие API/модель; он не разрешает рассогласование Alembic head. Перед заменой издателя полный остановленный журнал проверяется новой библиотекой на изолированной копии, включая `integrity_check` и точные данные.

Успех или доказуемая ошибка входа сохраняется вместе с неизменяемым результатом и исходящим журналом в одной SQL-транзакции. Публикация подтверждается только после Kafka ACK. Повтор завершённого запроса переочередяет прежний результат без вычисления и без изменения байтов. Повтор незавершённого не создаёт второго задания. Временная ошибка модели или хранилища не создаёт `CANCELLED` и не требует решения оператора: собственное задание возвращается в `PENDING` с паузой 30 секунд либо восстанавливается после lease.

`FAILED` разрешён только для неверного запроса, неподдерживаемого языка и доказуемо некорректного модельного выхода; он не принимается за готовую локализацию. Модельный сбой исполнения и timeout повторяются автоматически. Политики повторов и итоговую языковую проверку выполняет канонический владелец локализации.

Причина технического повтора записывается только ограниченным кодом в собственный `translation_job.error_code` и структурированный журнал с `request_id`, `correlationid` и `traceparent`. Частный модельный 503 сохраняет различие между deadline, незавершённой загрузкой, недоступным нативным процессом и некорректным ответом; worker отдельно различает недоступный socket, транспорт и HTTP-ошибку. Разрешённые коды определены в `src/translator_service/retry.py`; произвольный текст исключения или тела HTTP не переносится в диагностику. Неизвестная причина остаётся `TRANSLATOR_UNAVAILABLE`, старым строкам точная причина не приписывается задним числом. Эти внутренние коды не создают публичного `FAILED` и не изменяют Kafka-схемы или сохранённые результаты.

## Управление и восстановление

Первоначальная загрузка нативного вычислителя имеет отдельный предел `MODEL_STARTUP_TIMEOUT_SECONDS`: по умолчанию 600 секунд, допустимо положительное значение не более 1800. Он не увеличивает прежние 180 секунд модельного шага и 240 секунд запроса; повторная загрузка внутри запроса также ограничена оставшимся временем самого запроса. Docker `start_period` модели соответствует выбранному пределу загрузки, после первого подтверждения готовности действуют прежние пробы и пороги. Готовность до загрузки весов не объявляется.

Вычислитель сохраняет ссылку на принадлежащий ему дочерний процесс до подтверждённого завершения и reap. Истечение пятисекундного ожидания после `kill` не теряет эту ссылку, не разрешает второй процесс на том же порту и не перекрывает исходную причину запроса необработанным исключением. Пока завершение не подтверждено, новые запросы получают совместимый `503 / TRANSLATOR_NATIVE_NOT_READY`; исходный timeout запроса остаётся `TRANSLATOR_DEADLINE_EXCEEDED`. Подробная безопасная причина сохраняется собственным журналом. Установленный прежний worker понимает эти коды без обновления; Kafka-схемы и исполнение модели не меняются.

Команды `PAUSE`, `RESUME`, `RESET` требуют `command_id`, `actor`, `expected_revision`, `rationale`; журнал неизменяем. Идентичный повтор идемпотентен, изменение тела того же идентификатора и конфликт ревизии запрещены. Пауза останавливает выдачу новых lease, активная единица может завершиться. RESET требует отсутствия активного lease и возвращает только незавершённое в очередь; готовые переводы не удаляются.

Канонические данные находятся только в собственной PostgreSQL-базе `translator_service`; credentials и данные клиентов недоступны. Задания, исходные байты, результаты, outbox, карантин и журнал команд не имеют календарного удаления. Каждый клиент хранит собственную проекцию результатов. Резервная копия содержит собственную БД и точный digest контрактов и модели; восстановление проверяется в изолированной БД без доступа к рабочим topics. `verify-restored-state` проверяет head, контракт, исходные digest и точное соответствие результата outbox. После проверки незавершённые leases безопасно повторяются.

## Поставка и безопасность

Обновление SQL-ролей и отдельного издателя обязано согласовывать точную ревизию БД с ожидаемым head выбранных образов до допуска писателей; частичная выкладка не разрешает обход schema gate. Миграция 0005 добавляет checkpoints без изменения прежних заданий/результатов/команд, проверяется на восстановленной копии и повторно на замороженной рабочей БД. Порядок, технические fingerprint и ограничения совместимого отката определены в [руководстве](USER_MANUAL.md#согласованное-обновление-схемы).

Канонический модельный lock закрепляет SHA-256 и размер GGUF, ревизию нативного `llama.cpp` и профиль вычисления; `translator_ref` включает хеш весов и всего профиля. Образ содержит все веса, не скачивает их при исполнении и не обновляет автоматически. Нативный процесс является внутренней зависимостью Python-вычислителя, слушает только loopback `network none` контейнера и не создаёт публичного API. Старый Rust/MADLAD-вычислитель архивирован и исключён из сборки. Для модели в примере выделены 8 ГиБ; версии Python, Debian и Poetry сохраняются.

Исходный и целевой языки разрешаются по собственному каталогу 150 заявленных поставщиком языков и явным псевдонимам; неизвестные коды отклоняются без угадывания. `TRANSLATE_TEXT` сохраняет полный ограниченный текст: фрагментация и повтор обрезанного ответа не разрешают молча отбросить конец. Общий deadline остаётся ограниченным, а временный сбой и timeout оставляют задание для повтора. Кэш результата включает исходный и целевой языки; контекст чужого задания не становится входом следующего. Заявленный охват языков не заменяет смысловую проверку качества.

По [ADR-0110](../../../docs/adr/20261011-0110-translator-diagnostic-openapi-groups.md) все диагностические GET, включая состояние очереди, относятся к `default`; группа `translator` содержит только включённый операторский перевод. Это метаданные оформления: гарантии проверки здоровья, ответы и права не усиливаются и не меняются.

Порядок и состав трёх групп Swagger (`default`, `translator`, `metrics`) определяет [контракт операционного API](../../../docs/api/translation.md). Метаданные групп общие; частная схема содержит только пять GET, операторская — также POST перевода только при явном `API_TRANSLATION_ENABLED=true`. При `false` маршрута нет; обычная HTTPS/mTLS-диагностика не зависит от IdP, но локальное HTTP-чтение сохраняет OIDC. Существующие GET, ответы и проверки доступа сохраняются; задания создаёт только Kafka consumer. В HTTPS-режиме чтение по-прежнему защищено mTLS, включённый POST дополнительно требует собственный OIDC и отдельную роль. Недоступные/неверные обязательные для выбранного режима настройки пределов, OIDC или TLS закрывают запуск до listener.

Собственные Dockerfile, `compose.yml`, `.env.example`, PostgreSQL, миграции, одноразовый topic provisioner и автоматически экспортированные схемы достаточны для воспроизводимой сборки, настройки и запуска без исходников клиента. Обычный `compose.yml` по [ADR-0097](../../../docs/adr/20261009-0097-translator-kafka-dependency.md) включает канонический Kafka Compose с его отдельным `.env`; `compose.remote.yml` не запускает локальную Kafka и принимает маршрутизируемый защищённый endpoint. Provisioner использует отдельную deployment identity, автоматически выполняется после готовности Kafka, повторяется при временной недоступности и является обязательным барьером перед consumer, outbox и API; рабочие роли не имеют Kafka admin ACL и видят только `/run/secrets/kafka`, а provisioner — отдельный `/run/secrets/kafka-admin`. Database и telemetry identities также монтируются отдельно; status-admin доступен только одноразовой задаче. `/readyz` требует доступных собственной БД, Kafka и шести topics v1/v2. Локальная собственная БД остаётся на `internal` data network с `sslmode=disable`; удалённая production-БД требует `DATABASE_NETWORK_INTERNAL=false`, маршрутизируемой сети, `sslmode=verify-full`, CA, client certificate и key. По [ADR-0104](../../../docs/adr/20261010-0104-owner-contained-compose-recipes.md) самостоятельная и корневая композиции включают одну и ту же пару собственных `compose.remote.yml` и `compose.local.yml`: runtime объявлен один раз, локальная БД и ожидание Kafka имеют один рецепт владельца. Основной стек не меняется: Python 3.13.7, Debian Bookworm, Poetry 2.2.1; закреплённый нативный движок выбран ADR-0112. Сборка получает только закреплённые модельные артефакты; runtime не обращается к поставщику весов.

Unix socket и его том доступны только model и worker одной вычислительной ячейки. Вычислитель работает `network none`, остальные роли имеют только необходимые сети. Частный read-only API публикует `/healthz`, `/readyz`, агрегированный `/v1/status`, `/v1/components` и `/metrics`; он не принимает перевод и не возвращает тексты или результаты. Операторское исключение доступно только на втором listener с отдельным правом. Runtime исполняется непривилегированно, файловая система доступна только для чтения, заданы пределы памяти и CPU. Постоянные роли и подготовка topics по умолчанию ограничены `on-failure:3`; мигратор и остальные одноразовые задачи используют `no`. При обслуживании прежний меньший остаток или `no` задаётся собственными параметрами, не восстанавливается до исходных трёх попыток. Регистрация в существующем ограничителе требует живого точного экземпляра с пробой: отсутствие пробы, ручная остановка и исчерпанная история не обходятся ради регистрации. Native-выходы и восстановление `unhealthy` используют общий бюджет, не два независимых счётчика; прикладные повторы задания не являются рестартом контейнера. Production требует TLS, отдельных runtime и deployment identities, минимальных ACL, секретов, подписи образа и проверки независимого восстановления; локальный PLAINTEXT разрешён только для `AELEV_ENVIRONMENT=local`.

Логи содержат технические коды, идентификаторы корреляции, длительность и исход, но не текст перевода, SQL или credentials. Kafka consume/process/publish и HTTP-операции создают spans и продолжают входной `traceparent`; production требует HTTPS/mTLS OTLP endpoint. Собственный telemetry sender имеет постоянный журнал, собирает ограниченные Prometheus metrics и доставляет их вместе с logs/traces в центральный delivery; недоступность центра не удаляет локальный журнал. CLI выводит только запрошенный технический статус. Идентификаторы и точные байты перевода доступны как доказательства у владельца, не в обычном журнале.

Операционный API сохраняет частный HTTP listener с прежними путями для собственных проб и отдельный операторский listener в том же контейнере/процессе. Внешняя документация `/docs` показывает пять существующих операций чтения, включая `/v1/components`, и согласованный операторский POST через Kafka; она не раскрывает API модели. В HTTPS-режиме обязательны TLS 1.2+, отдельная CA операторов, клиентское удостоверение и отказ без сертификата; локальное исключение сохраняет ADR-0108. Закрытые CA/операторские ключи не доставляются runtime, серверный ключ получает только API. Swagger UI поставляется локально из закреплённого официального артефакта с digest, без браузерного CDN/валидатора. Завершение любого listener прекращает весь API; штатный сигнал закрывает оба. Собственный издатель объявляет `swagger_url` группы и компонента API по [общему техническому контракту](../../../docs/api/platform-ui-injection.md#ссылки-на-собственные-интерфейсы), остальные части ссылку не наследуют. Публичный origin, TLS/OIDC-файлы, ротация и команды принадлежат [README](ENDPOINTS.md).
