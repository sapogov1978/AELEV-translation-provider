# translator-service: нормативная спецификация

По [ADR-0109](../../../docs/adr/20261011-0109-operator-translation-through-kafka.md) операторский listener дополнительно принимает `POST /v1/translate` с отдельным OIDC-правом `operator-translate`. Прежние ограничения read-only ниже относятся к частному listener и диагностическим GET, а не к этому явно согласованному исключению. Вход публикуется только через штатный Kafka topic, не прямой записью задания или вызовом модели; API читает свой точный результат после ACK outbox. Определения входа, пределов, ошибок и неидемпотентного нового POST находятся в [контракте](../../../docs/api/translation.md#операторский-перевод). Перевод не является межсервисным HTTP-интерфейсом, а API не становится владельцем второго источника данных.

Локальное исключение операционного API по [ADR-0108](../../../docs/adr/20261011-0108-loopback-operator-http.md) выбирается явно HTTP origin в собственной конфигурации только при `ENVIRONMENT=local` и опубликованных loopback-портах. Документация/схема публичны, пять диагностических GET требуют собственного OIDC access token и client role `operator-read`; POST по ADR-0109 требует отдельного `operator-translate`. Issuer, audience, authorized party, подпись и сроки проверяются владельцем. HTTPS остаётся mTLS-режимом с дополнительным OIDC для POST, без автоматического HTTP при ошибке TLS. IdP сохраняет проверенное HTTPS, callback и origin точны, PKCE S256 обязателен. Административные OIDC-учётные данные доступны только собственной одноразовой задаче `provision`, не API. Исключение не касается межсервисного Kafka, iframe или удалённого размещения; прочие требования TLS ниже относятся к HTTPS-режиму.

Присутствие собственного издателя, штатная подтверждённая отписка и потеря связи определяются только [каноническим UI-контрактом](../../../docs/api/platform-ui-injection.md#присутствие-и-штатная-отписка) и ADR-0105. Отписка скрывает модуль без удаления журнала или изменения ревизии; отсутствие публикаций без отписки оставляет строку с потерей связи. Повтор и восстановление сохраняют владельца, UUID, последовательность и точные неподтверждённые байты.

Собственное состояние инъектируется по [техническому UI-контракту](../../../docs/api/platform-ui-injection.md) отдельной ролью `ui`: тип INFRASTRUCTURE, собственные БД, Kafka-соединение, consumer, модель, worker, outbox, API и издатель. Наличие UI/IdP не является зависимостью нативного запуска. Источник присутствия — только собственные heartbeat и локальная проверка модели в ячейке; техническая таблица `translation_runtime_presence` принадлежит переводчику, перестраивается следующими heartbeat и хранит строки сутки. TTL задаёт неизвестность, не удаление заданий или канонических результатов; heartbeat доказывает присутствие, не продвижение основной очереди. Единственная новая DDL применяется мигратором, не рабочими ролями. БД других сервисов и Docker API не читаются. Смысл read-only API и сохранность определены в [контракте](../../../docs/api/translation.md).

Общий инфраструктурный компонент владеет контрактом перевода, двумя входными Kafka topics, выходным topic, вычислением, закреплённой автономной Index-Translate 9B, собственной PostgreSQL-очередью и результатами. Назначение текста и решения клиентов он не знает и не изменяет. Публичная граница задана [Kafka-контрактом](../../../docs/api/translation.md), размещение и поставка — [ADR-0096](../../../docs/adr/20261009-0096-consumer-agnostic-scalable-translator.md), выбор вычислителя — [ADR-0112](../../../docs/adr/20261011-0112-index-translate-9b.md).

## Вход и вычисления

Вход — только `TranslationRequested` одной версии схемы через `translation.requests.priority.v1` или `translation.requests.v1`. Схема проверяет техническую identity издателя, но не закрепляет список клиентов. Отдельный consumer каждого topic проверяет артефакт схем, время, SHA-256 текста и идентификатор, транзакционно сохраняет точные байты до Kafka commit. Приоритет определяется только topic: 0 для приоритетного и 100 для обычного. Конфликт идентификатора или неверный контракт сохраняется в собственном карантине. При отказе БД consumer прекращает работу без commit и читает от последнего подтверждённого offset после перезапуска.

Работник получает одно задание с отдельным token и lease 360 секунд, используя `FOR UPDATE SKIP LOCKED`. Под блокировкой управляющей записи счётчик допускает не более настроенного количества последовательных приоритетных leases, после чего при наличии выдаётся обычное задание. Внутри класса порядок определяется `available_at`, возрастом и идентификатором. Просроченное задание может быть выдано вновь; завершение прежнего token запрещено. Внутренний вычислительный запрос ограничен 240 секундами, отдельный сегмент — 180 секундами. Зависший дочерний процесс прекращается и запускается заново; вычисления выполняются без внешней сети, веса проверяются по размеру и SHA-256 закреплённого `translator.lock.json`.

Независимый клиент использует общую операцию `TRANSLATE_TEXT` с исходным языком, целевым языком и текстом. Прежние `PROFILE_UNIT` и `OPERATOR_REVIEW` сохраняются только как совместимые значения v1. Независимые задания не смешивают входы или модельный контекст. Вычислительная ячейка состоит из локальной пары model + worker и собственного Unix socket; добавление одинаковых ячеек увеличивает пропускную способность без общего socket между узлами. Полный оригинал остаётся у клиента; перевод не входит в обучение как независимая метка.

Проверка готовности вычислителя успешна только после подтверждённой загрузки модели дочерним runtime. Во время его перезапуска или загрузки существующий процесс не считается готовым, а устойчивый вход и очередь не теряются.

## Устойчивый результат

Успех или доказуемая ошибка входа сохраняется вместе с неизменяемым результатом и исходящим журналом в одной SQL-транзакции. Публикация подтверждается только после Kafka ACK. Повтор завершённого запроса переочередяет прежний результат без вычисления и без изменения байтов. Повтор незавершённого не создаёт второго задания. Временная ошибка модели или хранилища не создаёт `CANCELLED` и не требует решения оператора: собственное задание возвращается в `PENDING` с паузой 30 секунд либо восстанавливается после lease.

`FAILED` разрешён только для неверного запроса, неподдерживаемого языка и доказуемо некорректного модельного выхода; он не принимается за готовую локализацию. Модельный сбой исполнения и timeout повторяются автоматически. Политики повторов и итоговую языковую проверку выполняет канонический владелец локализации.

## Управление и восстановление

Команды `PAUSE`, `RESUME`, `RESET` требуют `command_id`, `actor`, `expected_revision`, `rationale`; журнал неизменяем. Идентичный повтор идемпотентен, изменение тела того же идентификатора и конфликт ревизии запрещены. Пауза останавливает выдачу новых lease, активная единица может завершиться. RESET требует отсутствия активного lease и возвращает только незавершённое в очередь; готовые переводы не удаляются.

Канонические данные находятся только в собственной PostgreSQL-базе `translator_service`; credentials и данные клиентов недоступны. Задания, исходные байты, результаты, outbox, карантин и журнал команд не имеют календарного удаления. Каждый клиент хранит собственную проекцию результатов. Резервная копия содержит собственную БД и точный digest контрактов и модели; восстановление проверяется в изолированной БД без доступа к рабочим topics. `verify-restored-state` проверяет head, контракт, исходные digest и точное соответствие результата outbox. После проверки незавершённые leases безопасно повторяются.

## Поставка и безопасность

Канонический модельный lock закрепляет SHA-256 и размер GGUF, ревизию нативного `llama.cpp` и профиль вычисления; `translator_ref` включает хеш весов и всего профиля. Образ содержит все веса, не скачивает их при исполнении и не обновляет автоматически. Нативный процесс является внутренней зависимостью Python-вычислителя, слушает только loopback `network none` контейнера и не создаёт публичного API. Старый Rust/MADLAD-вычислитель архивирован и исключён из сборки. Для модели в примере выделены 8 ГиБ; версии Python, Debian и Poetry сохраняются.

Исходный и целевой языки разрешаются по собственному каталогу 150 заявленных поставщиком языков и явным псевдонимам; неизвестные коды отклоняются без угадывания. `TRANSLATE_TEXT` сохраняет полный ограниченный текст: фрагментация и повтор обрезанного ответа не разрешают молча отбросить конец. Общий deadline остаётся ограниченным, а временный сбой и timeout оставляют задание для повтора. Кэш результата включает исходный и целевой языки; контекст чужого задания не становится входом следующего. Заявленный охват языков не заменяет смысловую проверку качества.

По [ADR-0110](../../../docs/adr/20261011-0110-translator-diagnostic-openapi-groups.md) все диагностические GET, включая состояние очереди, относятся к `default`; группа `translator` содержит только включённый операторский перевод. Это метаданные оформления: гарантии проверки здоровья, ответы и права не усиливаются и не меняются.

Порядок и состав трёх групп Swagger (`default`, `translator`, `metrics`) определяет [контракт операционного API](../../../docs/api/translation.md). Метаданные групп общие; частная схема содержит только пять GET, операторская — также POST перевода только при явном `API_TRANSLATION_ENABLED=true`. При `false` маршрута нет; обычная HTTPS/mTLS-диагностика не зависит от IdP, но локальное HTTP-чтение сохраняет OIDC. Существующие GET, ответы и проверки доступа сохраняются; задания создаёт только Kafka consumer. В HTTPS-режиме чтение по-прежнему защищено mTLS, включённый POST дополнительно требует собственный OIDC и отдельную роль. Недоступные/неверные обязательные для выбранного режима настройки пределов, OIDC или TLS закрывают запуск до listener.

Собственные Dockerfile, `compose.yml`, `.env.example`, PostgreSQL, миграции, одноразовый topic provisioner и автоматически экспортированные схемы достаточны для воспроизводимой сборки, настройки и запуска без исходников клиента. Обычный `compose.yml` по [ADR-0097](../../../docs/adr/20261009-0097-translator-kafka-dependency.md) включает канонический Kafka Compose с его отдельным `.env`; `compose.remote.yml` не запускает локальную Kafka и принимает маршрутизируемый защищённый endpoint. Provisioner использует отдельную deployment identity, автоматически выполняется после готовности Kafka, повторяется при временной недоступности и является обязательным барьером перед consumer, outbox и API; рабочие роли не имеют Kafka admin ACL. `/readyz` требует доступных собственной БД, Kafka и трёх topics. По [ADR-0104](../../../docs/adr/20261010-0104-owner-contained-compose-recipes.md) самостоятельная и корневая композиции включают одну и ту же пару собственных `compose.remote.yml` и `compose.local.yml`: runtime объявлен один раз, локальная БД и ожидание Kafka имеют один рецепт владельца. Основной стек не меняется: Python 3.13.7, Debian Bookworm, Poetry 2.2.1; закреплённый нативный движок выбран ADR-0112. Сборка получает только закреплённые модельные артефакты; runtime не обращается к поставщику весов.

Unix socket и его том доступны только model и worker одной вычислительной ячейки. Вычислитель работает `network none`, остальные роли имеют только необходимые сети. Частный read-only API публикует `/healthz`, `/readyz`, агрегированный `/v1/status`, `/v1/components` и `/metrics`; он не принимает перевод и не возвращает тексты или результаты. Операторское исключение доступно только на втором listener с отдельным правом. Runtime исполняется непривилегированно, файловая система доступна только для чтения, заданы пределы памяти и CPU. Все постоянные роли используют `restart: unless-stopped`; миграция и provisioning одноразовые. Production требует TLS, отдельных runtime и deployment identities, минимальных ACL, секретов, подписи образа и проверки независимого восстановления; локальный PLAINTEXT разрешён только для `AELEV_ENVIRONMENT=local`.

Логи содержат технические коды, идентификаторы корреляции, длительность и исход, но не текст перевода, SQL или credentials. CLI выводит только запрошенный технический статус. Идентификаторы и точные байты перевода доступны как доказательства у владельца, не в обычном журнале.

Операционный API сохраняет частный HTTP listener с прежними путями для собственных проб и отдельный операторский listener в том же контейнере/процессе. Внешняя документация `/docs` показывает пять существующих операций чтения, включая `/v1/components`, и согласованный операторский POST через Kafka; она не раскрывает API модели. В HTTPS-режиме обязательны TLS 1.2+, отдельная CA операторов, клиентское удостоверение и отказ без сертификата; локальное исключение сохраняет ADR-0108. Закрытые CA/операторские ключи не доставляются runtime, серверный ключ получает только API. Swagger UI поставляется локально из закреплённого официального артефакта с digest, без браузерного CDN/валидатора. Завершение любого listener прекращает весь API; штатный сигнал закрывает оба. Собственный издатель объявляет `swagger_url` группы и компонента API по [общему техническому контракту](../../../docs/api/platform-ui-injection.md#ссылки-на-собственные-интерфейсы), остальные части ссылку не наследуют. Публичный origin, TLS/OIDC-файлы, ротация и команды принадлежат [README](README.md#swagger-операционного-api).
